# План доклада: «Кинетический манифест»

**Целевая аудитория:** Frontend-разработчики и архитекторы любого стека (React/Vue/Angular/Solid, любой стейт-менеджер)
**Длительность:** 35–40 минут
**Формат:** Концептуальный доклад с архитектурными инсайтами; Effector — рабочий пример реализации

**Главный тезис доклада:**
> Управление состоянием — это не выбор библиотеки, а выбор **мировоззрения**. Данные в современном вебе не лежат статично — они **движутся** через граф правил. «Кинетический» подход (event-driven + декларативность + реактивность) — это паттерн, а не фреймворк. Effector, RxJS, XState — лишь разные способы его реализовать.

**Что слушатель уносит:**
1. Понимание кинетического подхода как **способа мышления** (события вместо команд, связи вместо порядка).
2. Карту реализаций: что общего у Effector / RxJS / signals / стейт-машин и чем они различаются.
3. **Честный** ответ на вопрос «когда это стоит внедрять, а когда — overkill».

**Принцип построения:** подход — герой, библиотеки — иллюстрации. Ни один вывод доклада не должен зависеть от конкретного фреймворка. Код показываем на Effector (как на знакомом примере), но мысль — стек-независимая.

### Слайд 4: Два мировоззрения (честно, без соломенного чучела)

| | **Дискретное / императивное** | **Кинетическое / декларативное** |
|---|---|---|
| Состояние | снимок (snapshot), который ты мутируешь | поток через граф связей |
| Ты пишешь | **порядок действий**: «возьми, посчитай, положи» | **связи**: «когда X — следует Y» |
| Событие | повод вызвать функцию-обработчик | факт, который сам находит свои правила |
| Где живёт логика | в обработчиках, размазана по компонентам | в модели, отдельно от UI |
| Примеры | `useState`, Redux (классический), Zustand | Effector, RxJS, XState, signals |

**Важная оговорка вслух:** дискретный подход — не «плохой». Для половины задач он честнее и проще. Доклад не про «выбросьте useState», а про то, **когда и почему** второй взгляд оказывается мощнее. К trade-offs вернёмся в конце.

## Часть 1. Что такое кинетический подход (концепт, без кода) (10–12 мин)

### Слайд 5: Откуда метафора «кинетика»

**Честная оговорка для технического зала:** строго в физике движение тел изучает *динамика* (с силами) и *кинематика* (без причин); «кинетика» — про скорость процессов. Так что «кинетика» здесь — не учебник физики, а **имя из KRL** (Kinetic Rule Language, 2008). Берём метафору ровно за то, что в ней ценно:

| Физическая интуиция | В управлении состоянием |
|---|---|
| **Импульс** (толкнули) | **Event** — клик, ввод, сообщение из сокета |
| **Траектория** | путь данных через граф правил |
| **Трение** | `debounce` / `throttle` — гасим лишние события |
| **Препятствие** | условие/фильтр — пропустить или нет |
| **Результат движения** | эффект: запрос, запись, уведомление |

**Ключевой сдвиг:** состояние — это не «точка», а **траектория** в графе. Ты описываешь русло, а не толкаешь воду руками.

### Слайд 6: KRL — язык для «Живого Веба»

**Что это:** правило-ориентированный язык (2007–2008); программа = набор правил (rulesets), реагирующих на события. Часть open-source движка **KRE** (Kinetic Rules Engine).

**Кто создал:** **Фил Виндли** (Phil Windley), компания **Kynetx**. Эпоха Twitter/iPhone/открытых API — веб стал реактивным.

**Главная идея:** «Веб — это не страницы, это **потоки событий**». Каждый пользователь — «**personal cloud**»: облако правил, реагирующих на события его жизни.

**Три кита KRL:**
- **Entity orientation** — правила работают от имени сущности (юзер, устройство).
- **Event binding** — правила связывают паттерны событий с действиями.
- **Persistent values** — у правил своя «память» без БД.

**Salience:** событие «поднимается» (raise) для сущности — оно **не адресовано** конкретному коду. Правило само «подписано» на него. Декларативная, рассыпанная реакция — прямой предок инверсии контроля в Effector/RxJS.

### Слайд 7: ECA — сердце KRL

Каждое правило KRL устроено как паттерн **ECA (Event–Condition–Action)**:

```krl
rule good_morning {
  select when pageview url #example.com#   // EVENT: что случилось
  if morning() then                         // CONDITION: проверка
  notify("Welcome!", "Good morning!")       // ACTION: реакция
}
```
> В слайдах язык подсветки — `js` (Shiki не знает `krl`).

- **Event** — курок: без события ничего не происходит, в нём нет логики, только факт.
- **Condition** — предохранитель: не прошло — правило не «выстрелит». Нет «иначе» (как `filter` в `sample`).
- **Action** — пуля: изменение состояния / сайд-эффект / новое событие (цепная реакция).

**Зачем это в 2026:** ровно тот же ECA лежит под Effector (`event → filter → target`), под reducer'ами, под стейт-машинами. Подходу почти 20 лет — современные библиотеки его переоткрыли и оформили.

### Слайд 8: Три столпа кинетического подхода

Это то, что делает подход «кинетическим» — независимо от библиотеки.

**1. Event-driven: уведомление, а не команда**
Из определения евентных систем (KRL): есть три режима общения —
- *императивный*: «Сделай это!» (RPC, прямой вызов)
- *вопросительный*: «Сделаешь ли ты это?» (request–response)
- *декларативный (event)*: «**Это случилось**».

Событие не знает, кто и как на него отреагирует. Это инверсия контроля: смысл события задаёт **получатель**, а не отправитель. → слабая связанность.

**2. Declarative relations: связи вместо порядка**
Ты не пишешь «сначала А, потом Б». Ты объявляешь: «Б зависит от А». Порядок вычислит граф.

**3. Reactivity: граф пересчитывается сам**
Изменился источник → производные значения обновились автоматически, в один тик, без ручных вызовов.

### Слайд 9: Реактивность — это не изобретение фронтенда (Excel → сегодня)

Идея «данные движутся сами» старше React лет на тридцать.

| Год | Технология | Реактивность |
|---|---|---|
| 1979 | VisiCalc / Excel | `=A1+B1` пересчитывается при изменении ячеек |
| 1995 | Delphi / VB | data-binding: UI привязан к переменным |
| 2010 | Knockout / Ember | observable, уведомления об изменениях |
| 2013 | React | перерисовка дерева при смене стейта |
| 2015 | MobX | прозрачная реактивность («магия») |
| 2018 | Effector | реактивность через **явный** граф |
| 2020+ | Solid / Signals | fine-grained: обновляется только нужный узел |

**Вывод слайда:** кинетический подход — не мода. Это магистральная линия, которую фронтенд проходит уже 40 лет. Меняется только, **насколько явно** мы видим граф в коде.

## Часть 2. Как это реализуют — карта примитивов (9–11 мин)

### Слайд 10: Общая модель любой кинетической реализации

Под всеми библиотеками — одна схема:

```
[Источник события] → [граф правил/связей] → [состояние] → [UI]
        ▲                                         │
        └──────────── эффекты, новые события ◀────┘
```

И один и тот же набор «кирпичей», как бы он ни назывался:

| Роль | Effector | RxJS | Redux | Signals |
|---|---|---|---|---|
| Событие / намерение | `event` | `Subject` | `action` | (вызов сеттера) |
| Состояние | `store` (`$`) | `BehaviorSubject` | `reducer` state | `signal` |
| Производное | `combine` / `.map` | `combineLatest` | `selector` | `computed` |
| Связь / правило | `sample` | операторы (`pipe`) | `middleware` / saga | автозависимость |
| Сайд-эффект | `effect` | оператор + subscribe | thunk / saga | `effect` |

**Мысль слайда:** примитивы разные, подход — один. Дальше показываем код на Effector — как на знакомом примере, но идея переносится на любую строку таблицы.

### Слайд 11: Рабочий пример — Effector (явный граф)

Берём Effector как образец, потому что в нём подход виден буквально: **все связи явно записаны в коде**.

```ts
import { createEvent, createStore, createEffect, sample } from 'effector'

const todoAdded = createEvent<string>()              // событие (импульс)
const $todos = createStore<Todo[]>([])               // состояние
const saveFx = createEffect((t: Todo[]) => /* … */)  // эффект

// правило (ECA): когда todoAdded — взять $todos, добавить, положить обратно
sample({
  clock: todoAdded,
  source: $todos,
  fn: (todos, text) => [...todos, makeTodo(text)],
  target: $todos,
})

// другое правило: любое изменение $todos → автосохранение
sample({ clock: $todos, target: saveFx })
```

Прочитай вслух как ECA: *«когда (clock) случилось это, при условии (filter) — взять (source), преобразовать (fn) и направить (target) туда»*. Компонент при этом только дёргает `todoAdded` — логики в нём нет.

### Слайд 12: Соседи по подходу (вся карта, чтобы зал не думал, что кинетика = Effector)

Тот же подход, разные акценты — каждая библиотека делает явным **что-то своё**:

- **RxJS** — явные **потоки**. Первоклассная асинхронная композиция; кривая обучения крутая.
- **XState** — явные **режимы** (стейт-машины). Когда важно «в каком состоянии находится фича».
- **MobX / Solid / Signals** — fine-grained реактивность, минимум кода, «магия» автозависимостей.
- **Redux-Saga / Redux-Observable** — кинетический слой **эффектов** поверх дискретного Redux.

**Вывод части 2:** выбор библиотеки = выбор того, **что сделать явным**: граф (Effector), потоки (RxJS), режимы (XState) или вычисления (signals).

## Часть 3. Чем подход реально выигрывает (7–9 мин)

Концепция должна окупаться практикой. Три выигрыша, общие для всех реализаций (код — на Effector).

### Слайд 13: Выигрыш 1 — смерть race conditions

Императивно: между `await` состояние может «уехать».

```ts
async function checkout() {
  const cart = await getCart()   // ждём…
  const user = globalUser        // а если user сменился, пока ждали?
  api.buy(cart, user)            // какое состояние сейчас — неизвестно
}
```

Кинетически: значения берутся **в один тик**, атомарно.

```ts
sample({
  clock: checkoutPressed,
  source: { cart: $cart, user: $user },  // снимок состояния ПРЯМО СЕЙЧАС
  filter: $isAuthorized,
  target: buyFx,
})
```

Нет зазора для «дрейфа состояния». То же достижимо в RxJS (`withLatestFrom`) — это свойство подхода, а не одной библиотеки.

### Слайд 14: Трение — гасим лишние события (debounce / throttle)

Конкретизация метафоры «трения» со слайда 5 — теперь в коде.

Без трения: каждый символ ввода → запрос (`"react"` = 5 запросов, ответы вразнобой).
С трением:

```ts
sample({
  clock: debounce($query, 300),  // пауза 300мс — «трение»
  filter: (q) => q.length >= 2,
  target: searchFx,              // один запрос по устоявшемуся значению
})
```

**Мысль:** спам ввода — это лишняя «кинетическая энергия». `debounce` её гасит и защищает бэкенд; `throttle` — «вязкость» (пропускает ровным темпом). Операторы из `patronum`.

### Слайд 15: Выигрыш 2 — логика отделена от UI

- **UI:** только генерирует события и отображает состояние. Не знает про бизнес-логику и сайд-эффекты.
- **Модель:** события → связи → состояние → эффекты. Живёт без React/Vue.

Следствие: модель **тестируется без рендера** и переносится между фреймворками. Компонент становится тонким.

### Слайд 16: Выигрыш 3 — изоляция для SSR и тестов

Глобальное состояние ломается на сервере (один процесс — много запросов). Кинетические библиотеки дают изолированный экземпляр графа — в Effector это `fork()` + `allSettled()`:

```ts
// тест без мока React: дёрнули событие — проверили состояние
const scope = fork()
await allSettled(todoAdded, { scope, params: 'Test' })
expect(scope.getState($todos)).toHaveLength(1)
```

Тот же запуск работает и на сервере: скоуп на каждый запрос → нет утечки состояния между пользователями.

## Часть 4. Trade-offs: когда стоит и когда НЕ стоит (6–8 мин) ⭐

Самая честная часть. Без неё доклад — реклама.

### Слайд 17: Когда кинетический подход окупается

✅ Бери его, когда:
- **Много асинхронности и гонок** — параллельные запросы, отмена, оптимистичные апдейты.
- **Real-time / потоки** — сокеты, коллаборативность, живые данные.
- **Сложные зависимости между данными** — «это поле зависит от тех трёх, а кнопка — от всего сразу».
- **Бизнес-логику нужно тестировать** отдельно от UI.
- **Большая команда / долгий проект** — явные связи дешевле поддерживать, чем «археологию обработчиков».

### Слайд 18: Когда это overkill

⛔ Не тащи его, когда:
- **Маленькое приложение / локальный стейт** — состояние одной формы честнее на `useState`.
- **Прототип / MVP** — скорость важнее архитектуры; граф окупится позже.
- **Состояние в основном серверное** — часто хватает TanStack Query, а не полноценного графа.
- **Команда не готова к смене мышления** — кривая обучения реальна; навязанный паттерн = саботаж.

**Тезис:** кинетический подход — это инвестиция в сложность данных. Нет сложности — нет окупаемости.

### Слайд 19: Цена, о которой молчат

Честно про обратную сторону:
- **Дебаг графа.** «Откуда прилетело это обновление?» — без devtools/трассировки больно. Явный граф (Effector) тут легче, «магия» (signals/MobX) — тяжелее.
- **Spooky action at a distance.** Обратная сторона реактивности: изменил одно — где-то далеко среагировало. Неявные зависимости трудно держать в голове.
- **Выбор яда:** бойлерплейт (Effector) против неявности (signals/MobX). Бесплатно не бывает.
- **Линейность.** Последовательный императивный код иногда **просто читается сверху вниз** — граф так не прочитать.

### Слайд 20: Как внедрять, не ломая всё

- **Постепенно:** один сложный кусок (чекаут, фид, форма с гонками) — на кинетику; остальное оставить как есть.
- **Слоем поверх:** Redux-Saga / Redux-Observable добавляют кинетический слой эффектов без переписывания.
- **Сначала разделить UI и логику** — это даёт половину пользы и не требует менять библиотеку.

### Слайд 21: Бонус — кинетика не только метафора

Пуант доклада: тот же `sample` моделирует **настоящую физику** — скорость, инерцию, трение, доводку (lerp).

```ts
const tick = createEvent()       // пульс requestAnimationFrame
const $target = createStore(0)   // куда тянем (палец, цель)
const $pos = createStore(0)      // плавная координата

sample({
  clock: tick,                                          // каждый кадр…
  source: { pos: $pos, target: $target },
  fn: ({ pos, target }) => pos + (target - pos) * 0.15, // lerp = «доводка»
  target: $pos,
})
```

- Добавь `$velocity` и `* 0.95` за тик → **инерция** (Tinder-свайп, kinetic scroll).
- Физика живёт в графе, **в обход ре-рендеров** — стор двигает DOM напрямую (120 FPS).
- Тот же ECA: событие (кадр) → условие → действие. «Состояние» теперь — координата в пространстве.

Лёгкий «вкусный» слайд после серьёзных trade-offs. Пример: `examples/kinetic-motion.ts`.

## Заключение (3–4 мин)

### Слайд 22: Главные тезисы (стек-независимые)

1. Состояние в современном вебе **движется**, а не лежит. Кинетический подход моделирует это честно.
2. Подход = **три столпа**: event-driven (факты, не команды) + декларативные связи + реактивность.
3. Это **паттерн, а не библиотека**. ECA из KRL (2008) → Effector, RxJS, XState, signals.
4. Реализации различаются тем, **что делают явным**: граф / потоки / режимы / вычисления.
5. Главные выигрыши: нет race conditions, логика отделена от UI, тестируемость и SSR.
6. **Trade-off честно:** окупается на сложности данных и асинхронности; overkill на простом локальном стейте.

### Слайд 23: Что сделать в понедельник (без смены стека)

- Думай **событиями** («что случилось»), а не командами («что сделать»).
- Выноси логику **из компонента** — даже на голом React это уже половина пользы.
- Описывай **связи**, а не порядок шагов.
- Прежде чем тащить новую библиотеку — спроси: **есть ли у меня та сложность**, которую она окупает?

### Слайд 24: Финальная мысль

> «Кинетический стейт-менеджмент — это когда ты строишь русло, а не толкаешь воду. Ты не управляешь потоком вручную — граф управляет им сам, по правилам, которые ты объявил. Effector — лишь то, из чего сделано русло.»
